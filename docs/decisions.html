Specification review

Decisions before implementation

The original specification has a sound separation between source fidelity and logical consequence. It needs a narrower product scope and operational rules that prevent formal success from overstating documentary support.

What is retained

Keep source hashes and anchors, attributed statements, explicit assumptions, open-world reasoning, small models, theorem dependency checks, semantic review, and a coverage register. Preserve L0–L4 as separate assurance layers: source integrity, interpretation, model, proof, and audit explanation. Passing one layer does not establish another.

Decision register

IDDecisionReason / operational effect
D01 · scopeAudit supplied report findings only.User clarification replaces GENERATE and DUAL product modes. Independent rederivation is an audit technique, not generation of a competing original report.
D02 · outcomesSeparate evidence, argument, formal, and semantic-review states.A verified conditional theorem can coexist with missing premises. A conflict can coexist with a proof that the documents disagree.
D03 · support gapsInsufficient support is a first-class finding.Record the missing premise, search scope, citations examined, and evidence needed. Do not equate an invalid argument with a false conclusion.
D04 · reasoningEvery verdict includes an inspectable argument.Expose the original finding, exact question, evidence, rules, assumptions, steps, and limits; claim refutation needs a contradiction or relevant witness; argument rejection identifies the invalid inference.
D05 · open worldMissing information remains unknown by default.A closed-world assumption requires a named predicate, finite domain, period, and documented completeness basis. It is never global.
D06 · contradictionsStore positive and negative testimony with provenance.Do not import incompatible testimony as unconditional P and ¬P into one classical proof context. Prove documentary disagreement separately.
D07 · dependenciesPrefer concrete data and explicit theorem parameters.Custom axioms are disabled initially. Parameters still require source review: replacing an axiom with a parameter does not make a premise true.
D08 · scaleNo fixed document-count limit; bounded work and explicit coverage.Index on disk, chunk by source structure, process incrementally, and preserve cross-document links. Exhausted resources produce partial coverage, never silent truncation.
D09 · workspaceOne private temporary workspace per request.Inputs remain immutable; intermediate outputs and proof builds stay isolated. Export reproducible artifacts before cleanup.
D10 · independenceMinimal-context source/model review separate from proof construction.The reviewer sees the supplied finding and raw relevant sources, not the first agent's verdict as a premise. Shared-model errors remain possible and must be disclosed.
D11 · proof gateVerify every referenced theorem and its actual target.A successful build of an unrelated default target is insufficient. Pin dependencies, review axioms, audit target correspondence, and retain logs.
D12 · fixturesFive synthetic dossiers; two reports each.Correct and flawed reports are audited in separate runs. Expected answers are evaluator data, not evidence for the auditor.
D13 · languageAll repository artifacts in English.User conversation is in English. This rule is recorded in AGENTS.md.
D14 · delivery boundaryPrepare documentation and examples now.Skill instructions, schemas, scripts, and Lean validation await plan approval; no executable skill placeholder is advertised as complete.

Important gaps in v0.1

  • The four-case approval example tests a classification definition. It does not model “before execution”, exceptions, population scope, or a counterexample to the report's universal claim. The first implementation must add those obligations.
  • A flat status list mixes facts about evidence with facts about a proof run. A proof failure needs its own technical state; it is not a refutation.
  • A finite model must justify its domain. A counterexample to a universal finding is sufficient only when its membership, applicability, and violation are established.
  • Vacuous implications and empty populations can produce valid but irrelevant proofs. Require nonempty-domain or trigger witnesses where the reported conclusion presupposes them.
  • A source hash shows byte identity, not source authenticity or factual truth. OCR text needs anchors back to the original artifact.
  • Finding an inconsistent hypothesis set is itself valuable; proving arbitrary conclusions from it is unacceptable. Finite model witnesses are useful sanity checks, not a general consistency oracle.

Proposed defaults and decisions still open

Initial release decisions: local Markdown/text inputs and a required report and brief. Contract v2 now makes the brief optional and derives explicit criteria from each finding and the sources. Other retained decisions include no network enrichment unless authorized, core Lean before optional mathlib, no custom axioms, and no assumption that search is exhaustive. The approved extension now implements native PDF/DOCX/OCR with explicit provenance and uncertainty. Lean 4.24.0 is tested; see the extension and validation pages for executed scope, checker provenance, budgets and retained workspaces.

These are product design decisions derived from the supplied specification and the user's clarifications, not an assertion that the specification has already been formally verified.
